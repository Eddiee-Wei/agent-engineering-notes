# 06｜Agent Harness：从最小执行循环到工程化运行环境

假设用户交给 Agent 一个任务：**修复仓库中失败的认证测试，保留已有修改，并说明怎样验证结果。**

把错误日志和几份代码发给模型，它可以分析原因、生成补丁。但要完成任务，还需要读取真实仓库、应用修改、运行测试，再根据新的错误决定下一步。模型生成了“修复完成”，也不代表这些动作已经发生。

让这条链实际运转的，就是模型外围的执行系统。本文把它称为 **Agent Harness**：组织模型输入、驱动模型与工具交互，并处理运行边界与结果交付的软件。不同项目可能把其中一些责任放进 Agent、Runner 或 Runtime，术语没有统一的严格边界。

本章关注 Harness 内部怎样运行，以及什么时候值得增加工程能力；Tool、MCP、Skill、Plugin 的接入与封装关系是另一个视角。这里不会把这些能力排成成熟度阶梯，也不要求每个 Agent 都配齐生产平台的全部组件。

> 下文是公开资料支持的机制讲解与设计建议，核对于 2026-10-28。修复测试的过程是贯穿全文的假想案例，不是已完成的实验或生产复盘；示例流程不对应某个框架的可运行 API。

## 1. 先看清最小循环：谁建议，谁执行，谁继续

在修复认证测试的任务中，最小交互可以是这样：

```text
用户：修复认证测试，保留已有修改
                    ↓
驱动程序：组织任务、工具说明与当前观察，调用模型
                    ↓
模型：提出“读取测试和相关代码”的工具调用
                    ↓
驱动程序：检查调用，交给工具执行器
                    ↓
工具执行器：读取文件，把结果交回驱动程序
                    ↓
驱动程序：把结果加入下一次模型输入
                    ↓
模型：提出修改 → 执行器修改 → 返回结果
                    ↓
模型：提出运行测试 → 执行器运行 → 返回日志和退出码
                    ↓
继续修复 / 请求帮助 / 返回最终答复
```

这里有三个不同角色：

- **模型**根据当前信息提出下一步，例如读文件、改代码或结束回答。
- **循环驱动程序**组织请求、分派调用、收集结果，决定是否允许继续推进。
- **工具执行器**真正接触文件、进程或外部服务，返回执行观察。

工具结果需要关联到原调用，并在下一轮可见。测试仍然失败时，模型可以根据新日志重新定位，而不必在第一轮就猜出全部步骤。[ReAct](https://arxiv.org/abs/2210.03629v3)研究了推理、行动与环境观察交错的方式；OpenAI 对 [Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)的拆解则具体展示了协调用户、模型与工具的运行逻辑。

最小循环也需要停止条件。模型可以提出最终回答，用户可以取消，调用可能失败，程序也可以因超时或调用预算停止。**这些原因不能都记成“任务完成”。** 一个有上限的循环已经有用，不需要先实现复杂的恢复系统。

如果任务只是解释一段日志，由调用方提供完整材料、执行一次模型请求就可能足够；如果修复步骤严格固定，显式 Workflow 也可能更好维护。[Anthropic 的构建经验](https://www.anthropic.com/engineering/building-effective-agents)建议从满足需求的简单方案开始，因为动态 Agent 往往用额外延迟和成本换取灵活性。

## 2. 仓库一大，下一轮到底给模型看什么？

认证问题可能牵涉测试、配置、中间件和历史修改。把整个仓库与全部日志塞进每次请求，既昂贵，也容易淹没当前线索；只保留模型上一轮的结论，又可能遗漏关键事实。

Harness 需要选择本轮输入，例如：

```text
当前任务与项目说明
+ 与问题相关的代码、测试和配置
+ 最近的工具结果
+ 必要的历史与进度摘要
+ 当前可用工具和限制
→ 本轮模型请求
```

这不是要求自建一个统一“上下文编译器”，而是提醒实现者检查：模型实际收到了什么，材料是否仍对应当前工作区，哪些内容被裁剪或概括了。大工具结果可以只保留引用与有限预览，再按需读取；长历史可以摘要，但摘要应保留尚未完成的步骤和证据来源。

一个常见失败是：模型记住“认证测试已通过”，之后代码又发生变化，却继续引用旧结论。摘要是帮助恢复判断的材料，不是当前环境的保证。需要时仍应读取文件、查看 diff 或重跑相关检查。

Anthropic 的[长任务 Harness 复盘](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)记录了跨上下文窗口时一次尝试做太多、进度交接不清等失败；其增量工作与进度文件方案是针对这类长任务的经验，不是所有短任务的必备结构。更大的窗口或自动压缩，也不会单独解决进度真实性。

进一步的状态区分见 [03｜Agent 的状态边界](03-agent-state-semantics.md)。增加摘要、检索或文件化之前，先确认实际瓶颈是单条结果过大、历史累积，还是缺少必要材料，避免用更多存储掩盖输入选择问题。

## 3. 能调用 Shell，还要说明它在哪儿运行

模型提出“运行认证测试”，执行器可能跑在错误目录、旧代码版本，或缺少依赖的环境里。此时退出码和日志是真实的，却未必能说明用户工作区的状态。

对需要修改代码的任务，值得明确几项信息：

| 需要明确的条件 | 在认证测试案例中的作用 |
| --- | --- |
| 工作目录与代码基线 | 确定读写的是哪份仓库 |
| 开始前的已有修改 | 防止把用户内容覆盖或混入本次改动 |
| 命令、依赖与环境 | 区分代码缺陷和执行环境问题 |
| 可写范围与资源限制 | 约束修改、进程与临时文件的影响范围 |
| 测试与交付产物 | 让补丁、日志和验证结果对应同一状态 |

独立 Worktree 有助于隔离并行改动；一次简单的本地串行任务，也可以在明确基线和已有修改的前提下使用当前目录。是否需要容器或更强隔离，取决于代码信任程度、凭据暴露面和运行风险。

[SWE-agent 的研究](https://arxiv.org/abs/2405.15793v3)表明，面向 Agent 设计代码导航、编辑和测试接口会影响其行为与表现。这里值得借鉴的是反馈质量：例如明确区分命令失败、超时、仍在运行，以及输出是否截断，而不只是增加更多工具。

同时，不要把 `sandbox=true` 当作完整保证。文件、网络、进程和凭据的限制需要分别理解。容器内仍可能有可访问的秘密和外部服务；Worktree 隔离代码修改，也不自动隔离进程或网络。

这些选择有成本。额外工作区需要清理，容器有启动和依赖维护开销，日志归档也有保存期限。只保存任务需要的产物；对于要求审计或跨运行追溯的场景，再增加哈希、版本标识和持久归档。

## 4. 工具可用，不代表这次行动已经获准

修复文件、删除测试数据、安装依赖、推送提交，看起来都能通过同一个 Shell 完成，但用户授权范围可能完全不同。允许修复当前仓库，不自然延伸成允许发布版本或修改远端权限。

在有真实副作用的系统里，Prompt 中的行为约束应与执行点限制配合使用。可以从简单做法开始：明确可写路径、限制可执行操作，在超出任务范围或需要人工决策时暂停。涉及共享服务、多租户或高风险写入时，再设计更细的身份、策略、审批与凭据分发机制。

审批应足以让人知道批准的是哪个动作和资源，而不是泛泛的“继续”。已获授权且范围未变的低风险步骤，也不需要反复询问。门禁太细会造成审批疲劳，权限太宽则扩大错误影响面；取舍要围绕实际动作风险。

工具超时尤其需要谨慎：超时可能意味着尚未执行，也可能意味着操作已受理、只是结果没有送达。对于推送提交、发送消息或创建资源，应先查询真实状态，避免为了重拿结果而重复操作。纯只读查询的重试策略可以更宽，但仍要考虑成本和数据是否变化。

完整授权模型见 [07｜Agent 的授权边界](07-agent-authorization-semantics.md)。本章只保留一个判断：**执行权限由系统和当前授权决定，模型提出调用不能自行扩大权限。**

## 5. 任务中断以后，怎样知道该从哪里继续？

进度展示、暂停与恢复经常被混在一起。保存聊天记录后，下一次模型可以继续阅读，但程序未必知道测试进程是否仍在运行、某次写入是否已提交，或旧执行者是否还在工作。

对于短暂、可重做的本地任务，记录修改与失败原因、检查当前 diff 后重新开始，可能比恢复到每一步更划算。对于昂贵或必须跨进程继续的任务，才值得增加持久运行状态：任务标识、执行位置、待确认动作，以及恢复所需的版本和环境信息。[02｜Run、Attempt 与 Event](02-agent-runtime-semantics.md)解释了这类执行语义。

恢复认证修复任务时，可以依次问：

1. 保存的进度对应哪份代码与配置？
2. 上次工具是否已经执行，结果能否查询？
3. 当前是否仍有进程或其他执行者在修改同一工作区？
4. 哪些结果仍可信，哪些需要重新验证？

当系统有多个 Worker，并承诺故障后接管任务时，队列、租约或其他所有权机制才成为重要设计问题：要防止旧 Worker 恢复后与新 Worker 同时提交。长时间运行本身不必然要求这些组件；跨执行者接管与副作用要求才决定需要多强的保障。

Checkpoint 能恢复程序状态的一部分，不能回滚已发出的消息、Git Push 或数据库写入。需要可靠外部写入的场景，还要结合幂等键、操作回执、状态核对或补偿机制。**可恢复执行不等于外部操作天然 exactly-once。**

这些机制也带来存储、状态迁移和故障排查成本。应先定义能接受“重做任务”“恢复到最近保存点”，还是“核对每个未决动作后继续”，再选择实现。

## 6. 模型说完成以后，怎样验收？

在认证测试案例中，“已经修复”至少要能对应到本次修改和相关测试，而不只是模型的最终文字。交付可以说明：改了哪些位置、执行了什么命令、结果如何，以及哪些检查没有执行。

测试失败时还要区分原因：代码仍然有问题、环境缺依赖、测试服务不可达，不能为了得到成功终态而把它们混为一类。原先通过的测试，如果之后修改了相关代码，也应重新考虑其证明范围。

验收强度由任务决定：一处文字修改可能只需预览；代码补丁适合相关测试与 diff 审查；资金、权限或线上操作则可能需要独立环境检查或人工接受。测试通过只能证明被覆盖的条件，不等于所有需求正确。

对于程序化调用，还应区分“最后一个输出片段已送达”“运行已停止”“状态已保存”和“任务验收通过”。取消、预算耗尽、等待审批以及验证受阻，都应有清楚的结果。存在这些控制需求时，可以把运行状态和验收状态分开表达。

[Codex App Server 的公开设计](https://openai.com/index/unlocking-the-codex-harness/)展示了 Thread、Turn、事件和审批交互怎样通过协议暴露给不同客户端。这说明运行层可以被 CLI、IDE 或其他产品入口复用；界面展示结束，不应成为后台任务已经完成的唯一依据。

## 7. 按需扩展：多 Agent、评测与行为发布

上面的上下文、工作环境、权限、恢复和验收，是观察同一个运行系统的不同问题。它们可以分别改进，也不要求继续走向下面每一种架构。

### 多 Agent：有可拆分工作时，再考虑并行

两个 Agent 可以分别调查认证逻辑和测试环境，但这种拆分并不会自动提高正确率。它增加了任务分配、证据汇总和结果合并的成本，也可能重复研究或共享同一个错误假设。

需要并行修改代码时，隔离工作区或明确写入所有权能减少冲突。各分支测试通过，仍不代表合并后的补丁通过；集成者需要验证最终组合。只读研究则可以按来源、问题或证据范围分工，不必把每位参与者都建成完整持久任务系统。

多 Agent 与持久执行是独立选择：单 Agent 可以跨 Worker 恢复，多个 Agent 也可以在一次短请求中完成工作。详见 [05｜Multi-Agent 协作](05-multi-agent-collaboration.md)。

### 评测：反复运行或修改系统时，检查是否退化

一次认证修复成功，不代表换模型、Prompt、工具说明或上下文策略后仍然有效。如果系统会持续处理这类任务，可以积累代表性失败案例，比较完成情况、成本、延迟与人工返工，并记录实际影响行为的版本和配置。

Trace 有助于解释过程，测试与环境检查提供结果证据，两者用途不同。[OpenAI 的 Harness Engineering 复盘](https://openai.com/index/harness-engineering/)提供了让仓库知识、质量约束和日志反馈更容易被 Agent 使用的实践参考；它是特定团队的经验，不是所有项目都应复制的部署架构。

简单工具可以先用少量回归样例和人工抽查；多人共享或高影响系统，再按风险增加离线评测、灰度、监控和回滚。评测体系本身也有数据维护和执行成本。

### 事实记忆与行为规则：保存观察，不等于发布新策略

“本次认证测试在某版本上失败”是带来源和时间的事实记录，可以按产品约定进入会话或长期 Memory，并受权限、保留和纠错规则约束。它不必经过一次软件发布流程。

“以后所有认证失败都跳过某项检查”却是在改变行为，尤其可能影响权限和验收。把经验提炼成共享 Skill、Prompt 或 Policy 时，应核对适用范围、冲突与风险；高影响的规则变更适合先验证，再按受控流程发布。一次成功轨迹可以提供候选经验，不能单凭这一次成功就证明新规则普遍成立。

区分这两类写入，既能保留有用事实，也避免把“记住发生过什么”与“今后都按这个办法做”混为一谈。

## 8. 用问题选择能力，而不是按组件数量打分

回到最初的修复任务，选择 Harness 或补齐已有系统时，可以从实际故障往回找：

| 观察到的问题 | 优先检查 | 增加能力时的代价 |
| --- | --- | --- |
| 模型拿不到必要代码或被日志淹没 | 输入选择、工具结果预算、摘要 | 丢失细节、检索与维护成本 |
| 修改覆盖了用户内容，测试对不上版本 | 工作区基线、已有 diff、运行环境 | 环境与产物管理成本 |
| 工具可执行，但授权范围不清 | 执行点限制、任务授权、必要审批 | 策略复杂度与交互等待 |
| 中断后不知道动作是否执行 | 运行状态、回执与恢复核对 | 持久化与一致性成本 |
| 最终回答成功，实际测试仍失败 | 完成条件、检查结果与交付证据 | 验证时间与环境成本 |
| 并行后冲突更多，或升级后退化 | 拆分边界、集成验证、回归案例 | 协调与评测成本 |

这些不是成熟度分数，而是排查入口。先找到实际失败，再选择一个足以改善它的机制，并与简单基线比较：是否提高了完成质量，降低了返工或风险，是否值得新增的延迟与维护负担。

Harness 的工程价值体现在几个具体问题上：模型这轮看到什么，行动在哪里执行，当前允许做什么，结果怎样进入下一轮，失败后怎样处理，以及最后拿什么交付。回答清楚这些问题，比列出支持多少工具、Memory 或 Agent 更有用。
