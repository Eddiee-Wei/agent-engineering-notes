# 工具结果太大怎么办：把上下文预算与文件生命周期分开

一次工具调用执行成功，Agent 却可能在下一次模型请求时失败：工具返回的日志、查询结果或 JSON 太长，把上下文撑满了。

很自然的解决办法是把大结果写进文件，让模型按需读取。但接下来很容易越做越多：文件要不要上传对象存储？容器重建后是否恢复？历史会话里的引用要保留多久？多人共享会话该怎样访问？一个限制工具输出大小的改动，逐渐长成了文件持久化系统。

这次方案推演中，对我最有帮助的判断是：**先明确原文的使用期限，再决定存储和恢复机制。** 对允许过期的中间结果，可以只放在会话 Workspace；需要长期回读、审计或交付的内容，再显式保存为持久产物。

> 本文保留通用问题、取舍与验证方法，场景和示例均已抽象化，不包含业务数据或内部实现。文中方案是设计结论，不代表已完成生产上线或效果验收。公开资料核对于 2026-10-26，产品行为可能随版本变化。

## 1. 先定位：一次大返回，还是多轮累积？

两类问题看起来都像“上下文超限”，但修复位置不同。

| 情况 | 典型表现 | 应优先检查什么 |
| --- | --- | --- |
| 单次结果过大 | 某个工具返回后，下一次请求突然变得很大 | 工具最终输出大小、格式化是否膨胀、是否需要按需读取 |
| 历史持续增长 | 单条结果都不大，多轮之后才超过预算 | 历史窗口、摘要策略、重复材料和累计预算 |
| 两者叠加 | 大结果进入历史，随后每轮反复携带 | 先控制单条输入，再处理历史累计 |

调查时要沿着实际链路看：工具原始返回、最终生成的 tool message、写入会话的事件，以及发送给模型的请求。仅看工具 HTTP 响应或监控界面的截断预览，不能确定模型到底收到多少内容。

文件化能控制单条结果进入上下文的大小，但引用和预览同样会累积。它不能替代会话摘要，也不负责改变“本轮成功后再提交历史”这样的事务语义。

## 2. 三个独立问题，不要混成一个开关

| 问题 | 一个可能的答案 |
| --- | --- |
| 原文是否进入模型上下文？ | 小结果直接进入；大结果只进入引用与短预览 |
| 原文存在哪里？ | 内存、Workspace、线程状态或对象存储 |
| 原文需要保留多久？ | 当前运行、当前 Workspace、会话期限或长期 |

“移出上下文”并不自动意味着删除原文；“写成文件”也不自动意味着永久保存。框架里叫 `artifact` 的字段、对象存储里的文件、用户最终下载的报告，未必是同一种东西。接入前要看具体数据流，不能只看名字。

我最初考虑过“持久副本 + Workspace 缓存”：先保存原文，再同步到执行环境，文件丢失时重新下载。这个方案满足了旧引用可恢复的要求，也带来了版本、同步、过期地址和恢复时机等额外问题。

重新审视需求后，关键问题变成了：**我们是否真的需要承诺，每一份中间工具输出都能在未来重新打开？** 如果答案是否定的，就可以明确接受文件失效，省去这条自动恢复链路。若业务要求历史证据可复现，则应选择持久方案；重新查询可能得到不同数据，不能冒充原始快照。

## 3. 公开实现提供了哪些参照？

不同产品给出的答案并不一致。下面只列官方文档能够支持的行为，不把某一种配置推广成行业标准。

| 对象 | 大结果或上下文管理方式 | 生命周期启示 |
| --- | --- | --- |
| Deep Agents | 大工具结果超过阈值后写入配置的 backend，返回引用和预览，再读取或搜索 | 默认 StateBackend 的文件可通过 checkpointer 在同线程跨轮保留；也可选择沙箱 backend |
| Claude Code | 超过限制的成功 MCP 文本结果可保存为会话文件，模型获得文件引用 | 本地 `tool-results/` 随会话数据按保留规则清理，普通配置默认 30 天；不等于命令结束即丢 |
| Google ADK | Artifact 服务提供不同存储实现 | 内存后端进程结束后丢失，GCS 后端可跨重启保留；这是可选存储能力，不是所有工具输出的默认归档规则 |
| Microsoft Agent Framework | 提供上下文压缩策略，可裁剪或概括旧消息组 | 压缩针对模型可见历史，不能仅凭启用压缩就推断原始存储已经删除 |

对应资料：[Deep Agents 文件化](https://docs.langchain.com/oss/python/deepagents/context-engineering#offloading)、[Backend 选择](https://docs.langchain.com/oss/python/deepagents/backends)、[Claude Code MCP 输出限制](https://code.claude.com/docs/en/mcp#mcp-output-limits-and-warnings)、[Claude Code 应用数据目录](https://code.claude.com/docs/en/claude-directory#application-data)、[ADK Artifacts](https://adk.dev/artifacts/)、[Microsoft Compaction](https://learn.microsoft.com/en-us/agent-framework/concepts/agents/conversations/compaction)。

尤其要区分 Deep Agents 的“线程级状态”与“沙箱临时文件”。前者可以由 checkpoint 保存；后者是否存活取决于沙箱生命周期。官方[沙箱生命周期说明](https://docs.langchain.com/oss/python/deepagents/sandboxes#lifecycle-and-scoping)允许线程结束或 TTL 到期后环境消失。这能支持临时 Workspace 的设计，但不能写成“LangChain 默认随容器丢弃所有文件”。

这些资料支持的结论是：**控制上下文大小，与承诺原文可恢复，是可以分别选择的能力。**

## 4. 收敛后的流程：先判断大小，再文件化

不需要让所有工具结果都绕一遍文件系统。

```text
未做文件化：
工具执行 → 格式化结果 → tool message → 会话历史 → 下一次模型请求

启用文件化：
工具执行 → 格式化结果 → 检查最终文本大小
                        ├─ 未超阈值 → 原文进入 tool message
                        └─ 超过阈值 → 保存当前 Session 的 Workspace 文件
                                      ├─ 成功 → 引用 + 大小 + 短预览
                                      └─ 失败 → 有限失败说明 + 短预览
                                        ↓
                                  会话历史 → 下一次模型请求
                                        ↓ 需要更多细节时
                                  分段读取 / 搜索 / 代码分析
```

大小检查应覆盖**最终交给模型的文本**。如果只在业务工具返回时检查，后面的 JSON 包装、回调替换或文本拼接仍可能生成大消息。检查的位置还需要确保：写入历史和发送模型的路径都经过它，而不是只改变前端展示。

下面是用于讨论接口的合成示例，字段与数值不代表某个框架的固定协议：

```json
{
  "tool_executed": true,
  "result_id": "result_example_01",
  "storage": "workspace",
  "ephemeral": true,
  "size_bytes": 131072,
  "preview": "示例查询结果的有限预览……",
  "read_hint": "按关键词或字节范围读取所需内容"
}
```

原始工具调用 ID、错误性质，以及终端退出码、轮询游标等控制字段仍要保留。文件化改变的是大正文的传递方式，不应该让“执行失败”变成成功，或让模型丢失继续轮询所需的信息。

同样，不能把写文件失败描述成“工具没有执行”。业务动作可能已经完成，只是结果没有保存下来；此时回退整份大正文会重新引入超限，而自动重跑工具可能产生重复副作用。

## 5. Workspace-only 要把失效语义讲清楚

临时文件不是永远有效的链接。采用这种方案，就需要同时接受下面的行为。

**文件丢失是可表达的结果。** 读取工具应区分“已失效”和“暂时无法访问”。确认文件不存在或实例代际不匹配时返回 `result_expired`；权限错误、超时和网络中断应返回相应的读取失败，不能一律当作过期。

```json
{
  "status": "result_expired",
  "message": "当前 Workspace 中的原始结果已失效；需要时重新获取数据。"
}
```

**恢复执行环境不等于恢复旧数据。** 新容器仍需要正确建立会话目录和权限，后续工具才能继续工作；但不自动下载旧 tool result。引用可结合不重复的结果 ID 与 Workspace 实例标识，避免容器更换后误读同名文件。

**失效不触发业务重放。** 重新发起只读查询也要明确那是一次新查询。发消息、创建资源、提交任务等操作，不能为了“找回输出”自动再做一遍。连接断开且执行结果不确定时，优先核查实际状态。

**历史不会自动改写。** 会话中已有的预览和分析结论可以继续存在，但应把它们当作此前观察，不能假装已经重新读取原文。模型需要知道文件已过期，才能解释证据缺口。

**明确占用预算。** 临时不等于无限容量。除单文件上限外，还应按实际负载考虑会话总量、文件数量与清理规则；若执行环境长期活跃，单靠容器回收未必能控制磁盘增长。

## 6. 群聊共享的关键是会话身份与存储可达性

多人共享会话时，保存结果的用户和读取结果的用户可能不同。文件归属应使用经过服务端验证的共享会话作用域，而不是每次发言人的个人目录。

一个通用的逻辑划分是：

```text
应用 / 租户 / 共享会话 / Workspace 代际 / tool_result / 结果 ID
```

这是一种作用域示意，不建议把真实身份直接暴露到模型路径中。模型只传 `result_id`，服务端结合当前会话解析；不同租户、群组、会话仍必须隔离。操作者可以作为来源记录，但不能让文件的原创建者身份替代当前工具调用的权限判断。

还需要验证一个容易忽略的前提：**目录名相同，不代表底层文件共享。** 如果同一会话的请求会路由到不同服务副本，而这些副本使用独立的执行器，仅靠相同 Session ID 无法让文件互通。要么让同一会话访问同一可用 Workspace，要么明确接受切换后旧引用失效。跨实例可靠回读是额外的存储或路由要求，不能由命名规则代替。

## 7. 让“按需读取”真的有界

写文件只是第一步。如果读取工具又把整份文件传回模型，问题只是推迟了一轮。

- 同时限制行数和字节数，避免一行日志就有数 MiB。
- 返回明确的偏移、下一段位置和是否截断，处理 UTF-8 边界。
- 对 JSON 转义后的完整响应也做预算检查；控制字符可能让响应明显膨胀。
- 优先提供关键词搜索、字段选择或局部窗口，避免让模型机械地逐页读完整份文件。
- 保留原文是否已被上游截断的信息，文件化不能恢复本来就没收到的内容。
- 图片和其他多模态内容单独遵循协议，不把文本文件化规则直接套到二进制内容上。

单条工具消息的预算也应放在整体预算里看。并行返回的多份结果、系统指令、历史和预留输出空间都会占用上下文。字节阈值是便宜的近似保护，不等于精确 token 上限。

## 8. 我会怎样验证这类改动

下面是验收设计，不是已完成的线上测试报告。

| 场景 | 应观察到的行为 |
| --- | --- |
| 小于、等于、大于阈值 | 小结果原样；大结果进入引用分支 |
| 工具后处理替换或放大结果 | 最终消息仍受大小保护，模型请求与历史没有完整大正文 |
| 文件写入失败 | 有限失败说明；不回退大正文，不自动重跑业务操作 |
| 同一工具多次轮询、并行调用 | 不覆盖不同结果，控制字段保持正确 |
| 同会话另一位成员读取 | 文件仍存在且可达时能够读取；其他会话不能越界 |
| 执行器或容器更换 | 旧结果明确失效，新工具调用仍可正常使用环境 |
| 单行巨型日志、中文及转义字符 | 读取响应始终受预算限制，偏移有效 |
| 长时间持续会话 | 文件总量与上下文累计分别受到管理 |

文件写入本身也值得单独验证：不要假定远端文件 API 的“覆写”一定会截断旧内容。使用唯一目标或临时文件原子替换，并用长度、必要时用哈希核对内容。这里需要的是稳定的文件契约，不必因此引入历史文件自动恢复。

## 9. 什么情况下仍然应该保留持久副本？

如果用户需要下载报告、后续审核要求重现当时的数据、长任务必须跨容器恢复，或多个执行环境必须访问同一份快照，持久存储就有明确价值。此时应设计保存期限、访问权限、版本和恢复过程，而不是把它们藏在“文件化”的实现细节里。

对临时中间输出，我更倾向于先给出清晰的 Workspace 生命周期；对有交付或追溯价值的内容，再显式提升为持久产物。这次经验留下的判断顺序是：**先确定模型需要读多少，再确定原文需要活多久，最后选择存储方式。**
